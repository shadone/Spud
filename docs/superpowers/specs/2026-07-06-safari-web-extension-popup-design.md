# Safari Web Extension "Open in Spud" popup — design

Date: 2026-07-06
Status: Approved — ready for implementation plan
Scope: `OpenInAppExtension` (the "Open in Spud" Safari Web Extension). iOS Safari only (Spud is an iOS-only app).

## Problem

`docs/features/share-extension.md` is `Status: partial`: the Safari **banner**
(a content script) and the "Open in Spud" share/action extension both work, but
the Safari Web Extension's **browser-action toolbar popup** is the untouched
Xcode template — `OpenInAppExtension/Resources/popup.js` is literally
`console.log("Hello World!", browser);`, `popup.html` is `<strong>Hello
World!</strong>`, and `background.js` is the template `hello`/`goodbye` echo.

The content script (`OpenInAppExtension/Resources/content.js`) is fully built:
on the bundled allowlist of known Lemmy hosts (the manifest `content_scripts.matches`
array, generated by `scripts/generate-safari-matches.swift`) it shows a
dismissible "Open this in Spud?" banner on content paths (`/post`, `/comment`,
`/c`, `/u`), handing the page URL to the app via
`info.ddenis.spud://internal/resolve?url=<encoded href>`. It exports pure
helpers `isLemmyContentPath(pathname)` and `lemmyDeepLink(href)` and is covered
by a node test (`OpenInAppExtension/Resources/__tests__/content.test.cjs`).

The toolbar popup is the missing, always-available, user-initiated entry point.
Its value over the banner: it is reachable even after the banner is dismissed,
and on **any page** of a known instance — including the instance home, a
community list, or search — where the banner (content-path-only) never shows.

## Goal

Replace the Hello-World popup with a real one:

- **On a known Lemmy instance (any page):** a single enabled **"Open in Spud"**
  button. Tapping it hands the current page URL to the app via the same
  `resolve` deep link the banner uses.
- **On anything else** (google.com, or a Lemmy instance not in the bundled
  allowlist): an inactive **"Not a Lemmy instance"** message. No dead-end
  action.

"Known instance" = the same bundled allowlist the content script already runs
on. The popup does not detect Lemmy by host-sniffing or path shape; it treats
the presence of the content script (which the manifest restricts to allowlisted
hosts) as the single source of truth. This deliberately excludes Lemmy
instances that are not in the bundled allowlist — matching the user's decision
that the popup should act only on known instances.

## Approach: content script as the "known instance" oracle

The content script is declared (`content_scripts.matches`) only for allowlisted
hosts and auto-injects on all their paths (`*://host/*`). So **its presence in a
tab means "known instance."** The popup asks the active tab's content script;
a reply means known, silence means not-known. This keeps the ~500-host allowlist
single-sourced in the manifest, reuses the banner's proven navigation and
`lemmyDeepLink`, and adds the least new code.

(Alternative considered and rejected for now: the popup fetches its own
`manifest.json`, parses `content_scripts[0].matches`, and tests the active tab
host itself — self-contained but re-implements match-testing and navigates the
tab itself instead of reusing the banner's hand-off. Kept as the fallback if
iOS popup-to-content-script messaging proves unreliable; see Risks.)

## Components

### 1. `content.js` — extend (do not disturb the banner)

Add a `browser.runtime.onMessage` listener at the existing browser-only entry
point (guarded so the node test import stays side-effect free), handling two
message types:

- `{ type: "spud-probe" }` → respond `{ known: true }`. Presence of the listener
  (the script only runs on allowlisted hosts) is the "known instance" signal.
- `{ type: "spud-open" }` → `window.location.href = lemmyDeepLink(window.location.href)`
  — the exact hand-off the banner's Open button already performs. Reuses the
  existing `lemmyDeepLink`. Optionally respond `{ ok: true }`.

The listener responds on **any path** of the host (not just content paths),
which is what enables "any page of the instance." The existing banner logic
(shown only on content paths) is unchanged.

### 2. `popup.js` — new implementation (replaces the stub)

On load:

1. `const [tab] = await browser.tabs.query({ active: true, currentWindow: true })`.
2. Probe: `await browser.tabs.sendMessage(tab.id, { type: "spud-probe" })`, wrapped
   in try/catch plus a short timeout (a tab with no content script rejects or
   never replies).
3. A reply → render the **known** state (enabled "Open in Spud" button).
   Reject/timeout → render the **unknown** state ("Not a Lemmy instance").

On "Open in Spud" tap:

- `await browser.tabs.sendMessage(tab.id, { type: "spud-open" })`, then
  `window.close()`.
- If the send throws, keep the popup open and show a brief "Couldn't open" note
  rather than closing silently.

Extract the pure decision into a testable helper, e.g.
`popupStateFromProbe(result)` → `"known" | "unknown"`, so the state logic is unit
-tested independently of the async `browser` messaging.

### 3. `popup.html` / `popup.css` — replace the Hello-World markup

Two small states in the markup, toggled by `popup.js` (default hidden until the
probe resolves, to avoid a flash):

- **Known:** the Spud glyph/title + a primary "Open in Spud" button.
- **Unknown:** a muted "Not a Lemmy instance" line.

Native, compact styling. Accent teal matches the banner (`#30b0c7`). Dark mode
via `prefers-color-scheme`. All user-facing strings go through the existing i18n
mechanism (`browser.i18n.getMessage`, `_locales/en/messages.json`) with English
fallbacks, matching `content.js`'s `localized()` pattern; new keys are added to
`_locales/en/messages.json`.

### 4. `manifest.json`

- Add `"activeTab"` to `permissions` (currently `[]`) so the popup may message
  the active tab's content script on the user's toolbar tap. No broad host
  permission is requested — `activeTab` is granted per-invocation by the user
  gesture, consistent with the app's privacy posture.
- `default_popup` already points to `popup.html`; unchanged.

### 5. `background.js`

Gut the dead `hello`/`goodbye` template stub to an empty (or removed)
service worker — this flow is popup ↔ content-script direct; no background
coordination or native messaging is used. `SafariWebExtensionHandler.swift`
(the native `NSExtensionRequestHandling` echo) is not part of this flow and is
left unchanged.

## Data flow

```
tap toolbar button
  -> popup.html loads, popup.js runs
  -> browser.tabs.query -> active tab id
  -> sendMessage(tabId, {type:"spud-probe"})
       reply?  -> render "Open in Spud" (enabled)
       reject? -> render "Not a Lemmy instance"
  -> user taps "Open in Spud"
  -> sendMessage(tabId, {type:"spud-open"})
  -> content script: window.location.href = info.ddenis.spud://internal/resolve?url=<page>
  -> iOS opens Spud
  -> AppCoordinator.open -> .objectAtURL -> resolveObject
       resolvable (/post,/comment,/c,/u) -> navigates to the screen
       unresolved (instance home, /search) -> Haptics.warning() + log (see below)
  -> popup closes
```

## Error handling

- **Unknown host / no content script:** the probe rejects or times out → the
  popup shows the inactive "Not a Lemmy instance" state. No action is offered,
  so there is no dead-end tap.
- **Non-resolvable known-instance page (home, `/search`, etc.):** today
  `AppCoordinator.resolveAndDisplay` (`Spud/App/AppCoordinator.swift:103-135`)
  hits `.unresolved` and only calls `Haptics.warning()` + logs — no visible
  feedback. With "any page of a known instance" this path is exercised more than
  the banner exercises it (the banner only ever sends content URLs). This is a
  **known limitation and an explicit non-goal** of this change; improving the
  app-side `.unresolved` feedback (e.g. a "Couldn't find that page on `<host>`"
  toast) is a separate follow-up because it also affects the banner and other
  deep-link entry points.
- **Open-message send failure:** the popup keeps itself open and shows a brief
  "Couldn't open" note instead of closing.

## Testing

- **Node unit tests** (extend `OpenInAppExtension/Resources/__tests__/`, cjs,
  matching `content.test.cjs`): cover the new pure logic —
  `popupStateFromProbe(result)` mapping, and (already covered) `lemmyDeepLink` /
  `isLemmyContentPath`. Mock a minimal `browser` object if a light messaging
  test is worthwhile; otherwise keep the tested surface to the pure helper and
  leave the async wiring to manual verification.
- **Manual verification** (Safari Web Extension flows cannot be XCUITest-driven,
  and idb tap automation is dead in this project — manual verify is expected):
  enable the extension in the iOS Simulator's Safari settings, then:
  1. On `https://lemmy.world/post/<id>` — tap the toolbar button → "Open in
     Spud" → Spud opens to the post.
  2. On `https://lemmy.world/` (instance home) — button is enabled → tap →
     Spud opens (haptic-warn dead-end acknowledged above).
  3. On `https://www.google.com/` — popup shows "Not a Lemmy instance", no
     action.
- **No Swift/Xcode test changes** — the native handler is untouched and unused
  by this flow.

## Non-goals

- No app-side change to improve `.unresolved` deep-link feedback (separate
  follow-up; affects the banner too).
- No macOS support (Spud is iOS-only).
- No page-type-tailored popup copy (single "Open in Spud" everywhere on a known
  instance, per the minimal design chosen).
- No auto-redirect; the popup is user-initiated only.
- No change to the banner's behavior, gating, or appearance.
- No support for Lemmy instances outside the bundled allowlist (by design).

## Risks to validate first during implementation

- **iOS popup → content-script `sendMessage` under `activeTab`.** This is the
  one assumption to smoke-test before building out the UI. If messaging the
  active tab's content script from the popup is unreliable on iOS Safari, fall
  back to the rejected alternative (popup parses `manifest.json` matches +
  `browser.tabs.update(tabId, { url })` to navigate). The user-facing behavior
  is identical; only the mechanism differs.
